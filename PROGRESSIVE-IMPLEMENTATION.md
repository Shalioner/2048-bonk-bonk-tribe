# Opt-in последовательное углубление

Рабочая ветка `local/learning-budget-20261101`, baseline
`9b4120f1c2f1943b491d7378bcea18efd15a2350`.
Изменены только новая функция рядом с бюджетным решателем, её optional-привязка
в Python, CLI-переключатель и отдельные регрессионные проверки.

## Поведение и контракт

- Старый `solve_budget` побайтно совпадает с baseline. API остаётся 2,
  `DEFAULT_DEPTH=8`, `DEFAULT_THINK=10.0` и политика по умолчанию `legacy` сохранены.
- Новый `solve_budget_progressive` использует ту же сигнатуру, но буфер
  `info` должен содержать **10 double**, а не 8: первые восемь полей сохраняют
  смысл прежнего API; `[8]` — фактическая возвращённая глубина,
  `[9]` — запрошенная. Старый export по-прежнему пишет только восемь полей.
- Сначала готовится резерв depth1 при первом пороге. Затем целиком оцениваются
  все разрешённые направления на глубинах 2..requested. После достижения
  requested возможны уточнения остальных порогов на этой глубине.
- Каждый проход/направление создаёт собственный `eval_state`.
  Кэш не переносится между глубинами, порогами или вызовами решателя.
- Общий дедлайн и резерв `min(1с,25% бюджета)` распространяются на все проходы.
  Если полный следующий проход не завершился, возвращается последний
  завершённый уровень. Частичные результаты отдельных направлений не принимаются.
  Дополнительная проверка времени после оценки направления ловит короткий
  поздний фрагмент, не попавший на периодическую проверку C++.
- После первого завершённого прохода используется прежняя оценка роста
  `last_pass * growth`: слишком дорогой следующий проход может быть пропущен.
  Поэтому весь доступный временной бюджет не обязательно расходуется.
- `passes` считает полные timed-проходы, резерв depth1 в него не входит.
  При отсутствии таких проходов `fallback=true`, фактическая глубина1.
  Порог0 корректно записывается как0, а не как отсутствие порога.

Python: `bot.choose(board,depth,think,info,policy="progressive")`.
Старые вызовы без `policy` используют прежний решатель. Новый symbol optional:
старую совместимую API2-библиотеку можно загрузить и использовать в `legacy`,
но запрос `progressive` явно требует пересборку. CLI-проверка доступности и
положительной глубины выполняется до lock-файла и обращения к ADB.

Для будущего разрешённого запуска на телефоне предусмотрен флаг
`--search-policy progressive`. На телефоне в этой задаче ничего не запускалось.

## Проверки

```sh
rtk proxy sh vendor/build.sh
rtk proxy python3 -m unittest -v test_progressive_search.py
rtk proxy python3 bot.py --help
rtk proxy git diff --check
```

Сборка успешна. Девять новых тестов прошли за0.100с:

1. Достижение depth3 и совпадение выбора с fixed-depth оценками.
2. Уточнение порога только после достижения целевой глубины.
3. Правильный depth1 при нулевом бюджете.
4. Прерывание дорогой глубины сохраняет завершённый уровень>=2,
   и возвращённый ход совпадает с fixed-depth на этой фактической глубине.
5. Предел `budget+50мс` для 1/5/20мс и легальность ответа.
6. Legacy-dispatch без нового symbol и отказ opt-in на старой библиотеке.
7. Отказ от неизвестной политики/неположительной progressive-глубины.
8. CLI-отказ при неподдерживаемом symbol/глубине до любого IO.
9. Различение завершённого прохода при threshold0 и отсутствия прохода.

Однократный диагностический вызов на прежнем поле с двумя пустыми клетками,
запрос depth8, текущий baseline-кэш:

| Бюджет | Возвращённая глубина | Полных проходов | Fallback | Наблюдаемое search_s |
|---|---:|---:|---|---:|
| 0 | 1 | 0 | да | 0.000 |
| 5мс | 3 | 2 | нет | 0.001 |
| 20мс | 4 | 3 | нет | 0.011 |

Это демонстрация планировщика, не замер процента побед и не гарантия
производительности на другой машине/позиции. Полные партии и корпус10с не
запускались. Исходные `test_bot.py`, `test_benchmark.py`, `.command`, upstream
`vendor/2048.h`, эвристика и правила не менялись.

После интеграции исправления кэша и value-модели координатору необходимо
повторить эти регрессии и общие47 gates: стоимость lookup/cache/освобождения
памяти изменится. Никакой допуск бюджета для принятия этого изменения не ослаблен.
Перенос улучшения на рабочий depth8/10с и процент побед пока не доказан.
