# Точный контракт кэша поиска, 1 ноября 2026

Baseline: `9b4120f1c2f1943b491d7378bcea18efd15a2350`. Отдельная ветка
`local/learning-cache-20261101`; основной checkout, телефон и runtime не менялись.

## Изменение

Значение chance-узла кэшируется по `(board, remaining_depth, probability_bits)`.
`remaining_depth` — точная оставшаяся глубина, не «не менее такой глубины».
При положительном пороге `probability_bits` содержит все биты входной `float`
вероятности до деления на число пустых клеток. Для чтения битов используется
`memcpy`, без нарушения strict aliasing. При выключенном отсечении вероятность
на значение не влияет, поэтому поле ключа равно нулю.

Порог и spawn/value-модель должны быть неизменны в течение жизни `eval_state`.
Существующие solve-функции создают отдельные состояния для направлений/проходов.
Если будущий планировщик повторно использует состояние между порогами или моделями,
ему нужно очистить кэш либо расширить контракт; один точный ключ этого не разрешает.

`vendor/2048.h` и оригинальные upstream-файлы не изменены. Новый приватный тип
ключа поддерживает hash-контейнер и прежний map fallback. Эвристика, нулевой пол,
goal/loss, слияния и бюджетный планировщик сохранены.

Добавлен диагностический optional export:

```c
float score_levels_reference(uint64_t board, int move, int depth, float threshold);
```

Он вычисляет тот же поиск с теми же листьями и отсечением, но без кэша.
API остаётся 2; существующие обязательные символы и Python-интерфейсы не менялись.
Для ctypes задаются четыре argtypes и `restype=c_float`, как в новом тесте.

## Воспроизведение и регрессии

До правки выполнен новый тест `test_rotation_witness_no_longer_changes_decision`:
он падал на `AssertionError: 1 != 3`. Снимок из отбора seed202611016 после первой 11:

```text
0 0 0  0
0 1 1  0
0 1 3  0
2 3 2 11
```

Это тот же подтверждённый случай из `output/2048-research-20261101/RESEARCH.md`:
поворот менял R на D в исходной системе направлений. После правки тест проходит
при threshold0 и 1e-4, с сохранением допуска только на float-округления оценок.

Отдельно проверен depth-only мутант: в лабораторной копии текущего исправления
вероятностные биты заменены нулём. На seed202611010 cap1, depth4, threshold1e-4,
направление D он дал 1426017.0 против 1426037.0 у no-cache reference. Такой тест
не позволяет ограничиться заменой `<=` на `==` без вероятностного контекста.
Точный ключ даёт равенство с reference.

Пять новых проверок в `test_search_cache.py` покрывают:

- исходный свидетель и корректность преобразования направлений при повороте;
- отдельный случай вероятностного контекста;
- точное равенство cached/reference на четырёх реальных снимках при depth2/3/4
  и threshold0/1e-4; глубокий unpruned reference ограничен плотным полем;
- три поворота нескольких снимков, с абсолютным/относительным допуском округления;
- заблокированное поле, нелегальные направления и terminal goal.

## Цена точности: короткий локальный замер

Четыре поля: `SearchCacheTests.WITNESS` и три `SAMPLES`. Для всех легальных
направлений на depth3/4, threshold1e-4 получено 30 запросов. Каждый вызов API
создаёт свежий `eval_state`; таблицы строк предварительно прогреты. Три прохода
с циклической перестановкой порядка legacy/exact/reference. Измерялся
`time.process_time()` в одном Python-процессе, не конкурентное wall time.

| Поиск | Три CPU-времени, с | Медиана, с |
|---|---|---:|
| Legacy cache | 0.319612 / 0.169737 / 0.205292 | 0.205292 |
| Exact cache | 0.385659 / 0.293026 / 0.243315 | 0.293026 |
| No-cache reference | 2.527649 / 1.884625 / 1.662330 | 1.884625 |

На этом малом корпусе exact стоил примерно 1.43× CPU относительно legacy, оставаясь
примерно 6.43× быстрее reference. Все 30 exact/reference оценок побитно совпали.
Разброс повторов значим: это ориентир, не строгая оценка цены полных партий,
потребления памяти или поведения на 10 с. Новый ключ содержит больше контекста;
рост памяти и снижение количества hit возможны, но отдельно не измерялись.

Legacy-библиотека из предшествующей лаборатории имела SHA-256
`619ebe02dbffae4eb08e2606ad9905387e4242cd8656d111d171834f0d47e17c`,
текущая сборка exact — `66940a87df96f657198c323af566f127fa6001bece7366e3479f9f52751297fb`.
Пересборка на macOS может изменить бинарный SHA из-за UUID/пути; для происхождения
нужны также commit и исходники, не только старый бинарный SHA.

Новых полных партий не было. Эти снимки уже использованы прежними исследованиями:
это регрессии/диагностика, не новый независимый контроль побед. Смена действия
с R на D подтверждает исправление контракта, но не доказывает, что D выигрывает
чаще. Для решения об использовании при ограниченном времени нужен новый контроль
координатора с одинаковым бюджетом. Настройки телефона не переключались.
