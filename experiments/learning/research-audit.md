## 1. Новое подтверждённое свойство: поворот поля меняет выбранное действие

**Последствие:** при равномерном выборе клеток и изотропных правилах одинаковая задача после поворота может получить другой план. Нельзя считать все различия близких оценок свидетельством лучшей стратегии: часть различий создаёт приближение самого поиска. Это наследуется от baseline; нового дефекта в исследовательском diff не доказано.

**Проверка:** из `baseline/training.json` взяты все19 сохранённых незавершённых снимков первой/второй11; goal-снимки исключены. Для каждого рассчитаны четыре корневые оценки на depth3 и4, затем три поворота с обратным сопоставлением направлений. Получилось114 сравнений, четыре смены выбора, максимальная разница сопоставленных оценок5197.875. Это не114 независимых партий и не частота ошибки на полном игровом потоке.

Короткий свидетель — seed202611016, первая11, depth3, threshold1e-4:

```text
0 0 0  0
0 1 1  0
0 1 3  0
2 3 2 11

Направление в исходной системе:    U            D            L            R
Исходное поле:              1494258.5    1502495.5   1500815.125  1502521.5
Поворот90°, обратно mapped:  1494258.5    1502525.75  1500814.875  1502521.625
```

Исходно выбирается R, после поворота — соответствующий D. Это не точная ничья. На том же свидетеле смена выбора сохраняется при threshold1e-5 и0; одно ужесточение вероятностного порога её не устраняет. При threshold0 D =1502495.125 против1502526.875 после поворота; R =1502515.375 против1502515.25.

**Причина локализована в использовании cache на этом свидетеле:** после независимого обнаружения координатор выполнил отдельную лабораторную проверку с единственным C++ delta `CACHE_DEPTH_LIMIT=15→0`; данные прочитаны аудитором в `output/2048-research-20261101/rotation-probe.json`. Без cache на depth3 исходное и повёрнутое поле выбирают D; максимальная разница сопоставленных оценок падает с30.25 до0.25. На depth4 — с19 до0.375. Это причинная локализация наблюдаемой смены действия, не доказательство преимущества по победам.

**Не изолированы два механизма нарушения cache-контракта:** cache индексируется только `board` (`vendor/engine_adapted.cpp:19,292–294,363–377,400–402`). Возврат разрешён для сохранённого `entry.depth <= state.curdepth`: более глубокий горизонт может подменить точный текущий горизонт. При ненулевом пороге результат дополнительно зависит от `cprob`, но она не входит в cache-контракт (`359–361,381–392`). Изменение порядка обхода после поворота меняет, какая приблизительная оценка сохраняется первой. Какой из двух механизмов отвечает за каждое расхождение, пока не разделено; малая остаточная разница без cache совместима с float-округлением.

**Минимальная мера / цена:** расширить отдельный no-cache reference на короткий корпус; отдельно проверить cache с точным оставшимся горизонтом и явно совместимым контрактом вероятности/отсечения. На двух свидетелях сравнить score и выбранные действия при threshold0 и1e-4. Это локальная диагностическая правка, без архитектурного переписывания. Затем измерить цену cache и лишь после этого решать, нужен ли production-компромисс. Отключать cache во всём продукте заранее не предлагается: потеря скорости может уменьшить глубину и ухудшить результат. Ожидаемая польза — достовернее сравнивать методы и убрать зависимость от ориентации; улучшение процента побед не измерено.

**Приоритет:** P1 для точности следующего исследования; не доказанный блокер сохранённого результата29/60.

## 2. Наиболее содержательное направление качества: value по достижимости третьей11

**Факт:** в nonterminal листьях остаётся линейная комбинация табличных оценок строк/столбцов: пустоты, пары, монотонность rank^4 и штраф rank^3.5 (`engine_adapted.cpp:95–103,132–172,334–338`). Готовые11 исключены из пар слияния, но цель специфична: три несоединяемые11, занимающие рабочее пространство. Эвристика не является оценкой вероятности победы. Terminal отдельно задаёт1e9 (`334–361`). Это известное ограничение, а не новый баг.

**Гипотеза:** смена смысла value способна дать больший прирост, чем ещё один коэффициент пустоты: различать одинаковые по числу11 позиции по возможностям собрать оставшийся материал, безопасности свободной области и возможности свести большие пары. Уже проверенные `progress × count11` и число легальных направлений не исчерпывают эту задачу; `progress` после двух11 постоянен до победы, mobility не измеряет достижимость нужной пары.

**Минимальная мера:** на новом отборочном корпусе сохранять незавершённые позиции разных стадий и несколько независимых продолжений фиксированной политикой. Сначала короткая continuation-rollout/value с ограниченным числом запусков; затем, если метки содержат устойчивый сигнал, компактная стадийная табличная/n-tuple value. Данные для стадии0/1/2 готовых11 разделять по seed партии, включая позиции до второй11. Не обучать на нынешнем контрольном наборе и затем объявлять его независимой проверкой. Терминальные boards не заменяют такие метки.

**Существующая инфраструктура:** `benchmark.py:52–72` сохраняет только время достижения стадий и конечное поле; новый runner уже сохраняет первое поле каждой cap-стадии (`lab.py:83–104`). Поэтому для первого небольшого опыта не нужен новый общий фреймворк: достаточно расширенного диагностического корпуса вне продукта.

**Цена / эффект:** нужны новые метки продолжений и отдельная проверка качества, возможна дорогая симуляция и переобучение. Нельзя обещать рост побед без контроля. Проверяемая польза — ранжирование состояний по реальному целевому исходу, в том числе18/60 нынешних проигрышей до двух11. Число этих18 описывает старый контроль, не задаёт целевой ожидаемый прирост.

**Приоритет:** P1 как следующий существенно иной алгоритмический эксперимент после короткой проверки точности поиска.

## 3. Риск переноса поиска: весь незавершённый проход превращается в fallback depth1

**Факт:** рабочий решатель сначала считает depth1, затем запускает сразу заданную depth8 с порогами1e-4/1e-5/1e-6. Прерванный проход полностью выбрасывается (`engine_adapted.cpp:605–686`; `bot.py:263–272,320–330`). Нет промежуточного завершённого depth2/3/4, который можно было бы вернуть, если depth8 не успел. Fixed-depth `focus7` этого поведения не испытывает.

**Короткая проверка failure path:** на отборочном снимке seed202611011 с двумя11, `solve_budget(depth=8,budget=0.02)` вернул легальный U, `completed=0`, `cut=1`, `fallback=1`, около0.0178с,1,981,480 внутренних move-проверок. Это доказывает рабочую ветку деградации; не доказывает её частоту при10с. Нормальный путь уже подтверждён fixed-depth оценками реальных снимков. Дополнительно проверен integration edge: пара11 не сливается в C++; две11 не goal, три11 — goal.

**Условный риск:** если первый depth8-проход часто не завершается на актуальных плотных полях, реальный бот может играть depth1 даже при большом номинальном параметре. Неизвестное условие — частота и важность таких полей на машине/реальном бюджете; это нельзя вывести из зелёных тестов бюджета.

**Минимальная мера:** отдельный matched-corpus замер на одинаковом времени: нынешний режим против последовательности гарантированно завершаемых глубин и/или адаптивного сочетания depth/threshold. Записывать возвращённую глубину, completed passes, fallback/cut, число узлов и wall time. Сначала позиции, затем партии на новых seed. Изменение планировщика сохраняет API и не требует другого game engine. Углубление `focus7` имеет смысл сравнивать с альтернативой при равном бюджете, а не просто добавлять к depth8.

**Цена / эффект:** повтор вычислений на ранних глубинах и больше логики распределения времени; выигрыш — избегание резкого падения к depth1 при опоздании полного прохода. Процент побед и эффект на10с пока неизвестны.

**Приоритет:** P1 перед переносом новой политики на телефон, P2 для продолжающихся fixed-depth исследований. Это ранее учтённый gate; новая короткая проверка подтверждает механизм, а не объявляет его неожиданной регрессией.

## 4. Условный внешний риск: неизвестная spawn-модель может менять порядок стратегий

**Факт:** поиск и симулятор используют одну модель и равномерные клетки (`benchmark.py:20–34,46–48`; C++ `381–398`). Default основан на702 наблюдениях с pooling стадий10/11; уровни6+ имеют нулевые веса (`spawn-model.default.json:3–10`). `stage_row` берёт ближайшую меньшую стадию, при первом наблюдении новой стадии runtime копирует её счётчики и добавляет одно наблюдение (`bot.py:288–306`). Симуляция модель замораживает, телефон обновляет после хода (`403–409`). Это две разные системы принятия решений.

Pooling и нулевые веса уже явно записаны в README/SIMULATION. Их нельзя объявить неверными без данных телефона. Но ошибка модели на эндшпиле — существенная гипотеза: появляется событие, которому search приписывал ноль; уровень или клетка зависит от числа11/предыдущего хода; ranking кандидатов на симуляторе меняется. Наблюдение0 событий не доказывает точный ноль вероятности.

**Минимальная мера:** до переноса — аудит существующих наблюдений по стадии/числу11/клетке и небольшой заранее заданный sensitivity-эксперимент с раздельными solver-model/environment-model. Не менять default по догадке. Проверить, сохраняет ли кандидат преимущество при разумных вариациях редких уровней и клеток, включая незнакомый уровень с малым положительным весом. Если эффект меняется, сначала донаблюдать соответствующую фазу телефона. Новые наблюдения требуют отдельной разрешённой живой работы; здесь она не выполнялась.

**Цена / эффект:** несколько дополнительных моделей и партий, однако это дешевле дорого обучать value на неверной среде. Проверяемая польза — устойчивость выбранной политики и экономия исследования; улучшение выигрышей не обещается. Обучаемая value особенно зависит от этой границы: более точная аппроксимация неверного simulator не исправит перенос.

**Приоритет:** P1 перед утверждением о реальном win-rate; P2 для следующего офлайн-цикла.
