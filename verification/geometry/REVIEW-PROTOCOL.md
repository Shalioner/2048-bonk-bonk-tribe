## Итог после интеграции features

Независимо прочитаны feature commit `90b81ae9ca699e053b36dc44d81a50a351b361ec`, узкая оптимизация `19b3f8d83d9ba64d93b09f0f5f4970c7dd63f390` и уточнение cost-описаний `8d1dfb2c55cc449e74b07eca12cd26f2885ca518`. Проверены header, producer, места инъекций, native/reference тесты по исходникам и их контракт с runner. **Подтверждённых блокирующих дефектов в общей реализации до данных не обнаружено.**

- **Segments:** заменяется только штраф монотонности при создании row table. Линии делятся по рангам>=11; внутри сегмента сохраняются обычные ранги, включая0. Формула `(1-s)*original+s*sum(segment penalties)` соответствует описанию. Без CAP возвращается прежний original непосредственно. Move tables, rank sums и merge bonuses не изменены. Разворот переставляет направления и сегменты, сохраняя penalty; row/column применение обеспечивает D4 на уровне формулы. Полный float32 score сохраняет исходную погрешность порядка сложения, поэтому bitwise D4 для всего score не заявляется.
- **Geometry:** LUT считает каждое ортогональное ребро между non-CAP клетками один раз. Максимум вычисляется по всем маскам с тем же числом CAP; поправка `strength*(edges-maxEdges)` всегда<=0 и D4-инвариантна. Это мягкий leaf score: CAP не превращаются в неподвижные стены, легальность/terminal/pruning не изменяются. Таблицы инициализируются до поисковых потоков. Битовая маска>=11 корректна по nibble predicate; последняя оптимизация exact count использует отдельно ту же exact11 XOR/OR/popcount identity, что исходный core, и не смешивает goal11 с рангами12..15.
- **Risk:** helper вызывается на leaf afterstate с текущей строкой `spawn_table[get_max_rank(board)]`. Gating — ровно две11. При отсутствии пустот нет spawn-события; при>=2 пустот после spawn остаются и пустота, и плитка, а в связной сетке существует сдвиг на их границе, включая подвижные CAP. Поэтому R=0. При одной пустоте child полон: его может изменить только соседняя одинаковая пара ранга<11. Уже существующая пара делает все spawn безопасными; иначе безопасны ранги соседей пустоты<11 и rank11, дающий goal. Суммирование вероятностей остальных рангов с fixed rank order реализует именно заявленную one-spawn loss probability. Случаи generic12..15 и goal-after-spawn учтены. Для raw>=0 применяется объявленная мягкая поправка; отрицательный raw сохраняется, прежнее signed-max поведение не выдается за исправленное.
- **Producer/cache:** неизвестные kind/strength, nonfinite, несовпадающие/повторные anchors отклоняются. Самостоятельно исполнен только pure-Python producer на pinned bytes: baseline возвращает тот же объект без include, его SHA остаётся `257050c392bf3a743f894b0f674ff8d7da5c8f2165e2dff003f0e3b4192cb24d`; шесть source-вариантов изолированы. Cache/goal/moves/deadline/search ABI не инъецируются и не меняются. Новые оценки определяются board и неизменными в данном поиске strength/LUT/spawn; прежнего cache(board,remaining-depth,cprob) достаточно. Между вариантами используются отдельные libraries и новые поисковые caches.
- **Цена и протокол:** `8d1dfb2` исправляет plan/docs и `positions_scope`: segments — init precompute, geometry — mask/LUT, risk — closed form без production execute_move. Feature arithmetic не считается legacy positions, поэтому цена оценивается wall/depth. Независимо сравнён JSON: изменены только hypotheses/scope; arms, strengths, search, seed ranges, gates/history и bytes inventory сохранены. Текущий production core побайтно остаётся pure e28, новые формулы не приняты как default.

Root/worker native11 gates,192 cache/reference comparisons и150000 synthetic child checks использованы как контекст, а не собственное повторение. Здесь C++/native не исполнялись, библиотеки не собирались, партии и testsuite не запускались. Собственная проверка — source/diff, математическое рассуждение и чистая генерация bytes; native build/provenance и игровые результаты принимает координатор отдельно. Эта приёмка не доказывает повышение win-rate, равную actual cost, плато или оптимальность.
